The problem

Right now, an emergency is handled by whoever happens to be looking.

A soldering fire in the IoT Lab, an overheating GPU rack, a condensate leak by the server room — today they are all handled the same way. Someone notices. Someone shouts. Someone calls someone else. There is no sensing, no priority, and no way to know which lab needs help first when several fail at once.

How it works

One data path, end to end.

A zone node only ever sends raw numbers. Everything that matters — the score, the state, the ranking — is decided on the backend, so no single node can lie about being safe.

01

Zone node senses

An ESP32 samples flame, gas, water level and motion, then publishes the raw values over Wi-Fi — no score, no verdict.

02

Backend fuses a score

The server validates each reading, debounces it, and combines all four hazards into one 0–100 risk score per zone.

03

Priority engine ranks

When two or more zones cross critical, they're ordered by risk, then occupancy, then how long they've been critical.

04

Dashboard shows first

Security sees a live map, a ranked queue that explains itself, and the full incident history — in real time.

What it senses

Four signals, weighted by how much they matter.

Fire carries the most weight because it escalates fastest in a room full of electronics. Occupancy is lightest on its own, but it becomes the tie-breaker the moment two zones are critical together.

Fire

Flame sensor, debounced over consecutive samples so a flicker never trips a false alarm.

40/ 100 weight

Gas & fumes

MQ-2 reading, normalised and suppressed during warm-up, rising in proportion — not one jump.

25/ 100 weight

Water / flood

Level sensor at the lowest point under cooling gear, where a condensate leak pools first.

20/ 100 weight

Occupancy

PIR presence with offline detection, so an empty zone is never confused with a dead sensor.

15/ 100 weight
// computed on the backend, never trusted from the node
risk = 40·fire + 25·gas + 20·water + 15·occupancy  → 0–100
SAFE < 30  ·  WARNING 30–64  ·  CRITICAL ≥ 65 (with hysteresis)
Why trust it

Built for the one shift where everything goes wrong at once.

Server-side scoring

A node can send raw numbers, never a verdict. The backend alone decides SAFE, WARNING or CRITICAL.

Sub-second cut-off

On CRITICAL, the buzzer, red LED and relay cut-off fire together in under a second, logged with a timestamp.

Role-based access

Staff view and acknowledge. Only admins override. Enforced in the API, not just hidden in the interface.

Survives a restart

Lose power or restart the backend and it rebuilds live zone states from the database — nothing is assumed safe.

Offline is not safe

A silent node shows OFFLINE, never a false SAFE, so a disconnected sensor can't hide a real hazard.

Every incident, logged

Each state change is its own row, so you get a full timeline from first trigger through acknowledgment to recovery.
